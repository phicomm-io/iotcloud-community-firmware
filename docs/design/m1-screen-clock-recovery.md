# M1 原厂 MCU 屏幕校时补发

用户反馈：0.9.27 与 1.0.0-rc.5 都可能在 NTP 成功、温湿度正常时仍显示 2000-01-01；修改时区后恢复。该现象支持首次时间下发未生效的方向，但尚无故障机串口抓包确定原因。

## 协议参考与边界

对照配套 MCU 仓库 `phicomm-io/phicomm_m1_mcu_atsamd20` 的
`01af1ebccdaf48b73d02eaaf7023f68d5a0d280f`：

- `docs/protocol.md` 的 `03` 设置时间帧：大端完整年份、月日时分秒，与本仓库 `m1_clock_frame()` 一致。
- `docs/stock-analysis.md` 的原厂 `i2c_rtc`（0x5370）与 `sem_task` 分析：RTC、显示拥有独立任务/调度，不能把联网模块获取 NTP 当作显示更新完成。

本次参考已有原厂 MCU 逆向资料，并直接核查原厂 11.1.2.1 MCU 备份：`0x8768` 的命令 13 分支在 `0x877c–0x8782` 构造 `23 0d` 回复，`0x8784` 起输出完整年份与月日时分秒。支持主动查询，不能把串口写入成功当成 RTC 已更新。

原厂 Wi-Fi 备份的 SNTP 路径为初始化立即校时、之后每小时校时，成功回调单次发送 `03`，没有 MCU 读回确认。本次新增确认和限次重试，不声称原厂也有此策略。

## 行为

保留现有 NTP 小时周期及失败 60 秒重试。NTP 入队事件与 MCU `17` 启动公告触发一个 UART 线程独占的事务：

1. 从最新软件 UTC 和当前时区构造 `03` 设置帧。
2. 等待 250 ms，再发送 `0d` 查询帧。
3. 仅在查询后的 2 秒窗口接受 `0d` 回复，并与当前软件本地时间比较，允许 ±2 秒偏差；通过逐个候选日期比较自然覆盖月末、年末、闰日和午夜，不接受非法日期。
4. 写入/查询发送失败、查询超时或读回不一致，1 秒后重新从当前时间下发；总计最多 3 次尝试，耗尽后记录 unconfirmed 日志并停止。成功记录 confirmed 日志并停止。

没有每 60 秒补发。`0c` 主动广播不作为查询回复；无事务时忽略时间报告。固件时钟读取失败也受尝试上限约束。主控升级、Wi-Fi OTA 和待重启期间暂停；恢复后废弃旧查询，重新进入限次下发流程。重试不依赖 DNS、网络或 FIFO 空间。后续 NTP 成功或 MCU 启动通知可以开始新的事务。

`ntp_screen_queued` 保持原本入队语义，不能当作 MCU 确认标志。MCU 读回确认通过日志报告。读回一致证明 MCU 报告的时间一致，不能替代屏幕可视验证。

## 验证

`python3 tests/test_m1_clock.py` 保留原 NTP 用例；
`python3 tests/test_m1_screen_clock.py` 编译生产事务函数，覆盖成功读回、错误时间、非法日期、主动广播忽略、读回超时、下发/查询发送失败、最多三次、时钟读取失败、时区变化、升级/重启暂停、午夜跨日、毫秒回绕以及成功/失败后不再周期发送。

实机待验证：原厂 MCU 冷启动联网且不修改时区，检查 confirmed 日志及屏幕；丢弃首次设置帧后观察查询不一致与重试；丢弃查询回复观察超时与三次上限；MCU 重启、断网、时区变更及升级暂停。主机测试和构建不能代替设备验收。
