# 斐讯 A1 免拆刷机：内网上传与公网 DNS 迁移

A1 原厂固件保留了局域网固件上传接口，也能向服务器检查并下载更新。设备联网后，可以研究通过这两条原厂 OTA 路径迁移到社区固件。

**本文是基于原机备份的待实机验证指南：接口调用链已确认，但目前没有随文提供经过这份原厂固件安装、启动验证的迁移镜像，也没有可直接填写的公共迁移 DNS。取得适配镜像前，先完成联网和只读接口检查，停在上传之前。**

本文的 A1 指空气净化器，不是 TC1 插排的 A1 硬件版本。支持 Windows PowerShell、macOS 和 Linux；选择电脑系统后查看相应命令。

本文分析范围为原厂 A1 `v1.47`；其他版本需另行核对接口和镜像兼容性。

<!-- os-picker -->

## 1. 选择适合自己的路径

| 路径 | 用户如何操作 | 还需要什么 |
| --- | --- | --- |
| 内网免拆 | 电脑在同一局域网上传迁移镜像 | 适配的 A1 原生 OTA 镜像、设备 IP |
| 公网免拆 | 设备通过路由器 DNS 访问兼容升级服务，再主动下载镜像 | 兼容服务、可控 DNS、适配镜像，以及满足原厂检查条件 |

内网上传不依赖原厂云端和定时检查，适合先验证。公网方案适合后续向用户交付统一迁移服务；“修改 DNS”只改变访问目的地，不会自动生成升级服务。

## 2. 先让 A1 联网

已经在路由器客户端列表中的 A1 无需重新配网。如果保留着旧 Wi-Fi 配置，可以继续使用；更换路由器后也可复建旧名称、密码及兼容的加密方式，让设备尝试自动重连。

全新或无有效网络配置的设备可尝试电脑 EasyLink 工具。电脑先无线连接目标 2.4 GHz 网络，下载并解压 [EasyLink 工具包](assets/tools/a1-easylink.zip)，进入 `a1-easylink` 文件夹后启动：

<!-- os:windows -->

```powershell
py -3 .\a1_easylink_web.py
```

<!-- /os -->

<!-- os:mac linux -->

```sh
python3 ./a1_easylink_web.py
```

<!-- /os -->

在本机页面填写参数并发送；同时需要触发 A1 进入配网监听。已确认固件中的触摸输入约 1 秒阈值，但对应面板图标尚未实机核对。完整流程与限制见 [A1 / M1 配网指南](stock-provision)。

## 3. 内网：确认连接目标设备

电脑通过 Wi-Fi 或网线连接 A1 所在路由器，确保双方可以直接通信。从路由器客户端列表取得 A1 的 IP，替换示例地址：

<!-- os:windows -->

```powershell
$DeviceIp = "192.168.1.123"
curl.exe --noproxy "*" --connect-timeout 3 --max-time 5 "http://${DeviceIp}:8000/config-read"
```

<!-- /os -->

<!-- os:mac linux -->

```sh
DeviceIp="192.168.1.123"
curl --noproxy '*' --connect-timeout 3 --max-time 5 "http://${DeviceIp}:8000/config-read"
```

<!-- /os -->

响应后核对可识别的设备信息与路由器中的 MAC；不通时先查 IP、客户端隔离和网络互通，不进入上传步骤。

这里不需要 TFTP、TC1 的附加网卡地址或 JSON `FILENAME` 触发文件。A1 的接口直接接收固件正文。

## 4. 内网：准备迁移镜像并上传

需要专门适配 A1 原厂 OTA 加载路径的原生迁移镜像，目标社区版本至少为 **0.9.21**。版本达到要求仍须验证原厂安装兼容性；发布方应明确适用的原厂范围、文件哈希、首次迁移方式及启动后的访问方法。文件改名不能改变兼容性。

完整 Flash 备份、`.all.bin` 和社区 OTA 的 `.signed` 封装均不能直接当作该接口的正文；带 `.raw` 后缀也不自动代表已适配。这些文件服务于不同安装路径。

取得**已经验证兼容**的迁移包后，按其说明放到当前目录。以下 `a1-migration-native.bin` 是示例文件名，不是文章已提供的下载文件。

先核对 SHA-256 与发布方公布值一致：

<!-- os:windows -->

```powershell
Get-FileHash -Algorithm SHA256 .\a1-migration-native.bin
```

<!-- /os -->

<!-- os:mac -->

```sh
shasum -a 256 ./a1-migration-native.bin
```

<!-- /os -->

<!-- os:linux -->

```sh
sha256sum ./a1-migration-native.bin
```

<!-- /os -->

保持供电及网络稳定，上传一次：

<!-- os:windows -->

```powershell
curl.exe --noproxy "*" --connect-timeout 5 --max-time 300 --header "Content-Type: application/ota-stream" --header "Expect:" --data-binary "@a1-migration-native.bin" "http://${DeviceIp}:8000/OTA"
```

<!-- /os -->

<!-- os:mac linux -->

```sh
curl --noproxy '*' --connect-timeout 5 --max-time 300 --header 'Content-Type: application/ota-stream' --header 'Expect:' --data-binary '@a1-migration-native.bin' "http://${DeviceIp}:8000/OTA"
```

<!-- /os -->

原厂接收逻辑将数据写入 OTA 临时分区，累计 CRC16，保存升级信息并请求重启。命令没有设置自动重试；若超时或连接断开，先观察设备及路由器状态，不立即重复上传。

## 5. 公网：DNS 迁移如何工作

公网方案由 A1 主动发起连接，不要求把设备的 8000 端口映射到互联网。兼容服务可以部署在公网，DNS 配置由用户自己的路由器或受控 DNS 完成。

```text
A1 已联网
  → DNS 将相关原厂域名解析到兼容服务
  → 完成设备所需的激活 / 状态交互
  → 原厂固件检查更新
  → 获得镜像 URL、MD5 和升级标志
  → 下载、校验、写入并重启
```

这份备份引用的主要接口为：

| 用途 | 原厂地址 |
| --- | --- |
| 激活 | `https://phicloudsym.phicomm.com/device/active?mac=…&productId=30` |
| 检查更新 | `https://aircleaner.phicomm.com/aircleanerfirmware/checkUpdate` |
| 长连接业务 / OTA 指令 | `aircleanerconnecter.phicomm.com:9000`，另有旧地址兼容分支 |

这些地址来自固件，并不表示已核验它们当前在线。首次迁移应仅针对自己的目标设备，保留原有 DNS 配置以便结束后恢复。

### 用户侧 DNS 设置与检查

这一流程以服务维护者已公布**完成目标设备验证的 DNS 地址和迁移镜像**为前提。目前尚无随文可用的地址，不能把示例主机名当成现成服务。

1. 记录路由器原来的 DNS 设置和设备网络信息。
2. 在设备所在网络的路由器 DHCP / LAN DNS 设置中，填入维护者提供的地址；部分路由器由自身代理 DNS，需同时按维护者说明设置转发。只改电脑 DNS 不会让设备自动使用它。
3. 按路由器说明让设备重新取得租约、刷新解析；不要在传输或写入固件时重启设备。若设备使用静态 DNS，需另行确认其实际解析去向。
4. 用同网电脑查询更新域名，确认解析结果符合维护者公布值；再由兼容服务日志确认**目标设备自身**的激活、更新检查和下载请求。

<!-- os:windows -->

```powershell
Resolve-DnsName aircleaner.phicomm.com -Type A
```

<!-- /os -->

<!-- os:mac linux -->

```sh
dig +short A aircleaner.phicomm.com
```

<!-- /os -->

电脑查到新地址只证明电脑的解析结果，不能证明设备也已使用该 DNS，更不能证明已刷写成功。迁移完成后恢复用户原有 DNS，避免继续依赖临时服务。

### 给服务维护者的响应结构

检查更新的候选 JSON 如下。URL、MD5 和版本仅用于说明格式，不能直接部署为真实升级清单：

```json
{
  "url": "http://migration.example/a1-native.bin",
  "md5": "<实际下载正文的32位MD5十六进制>",
  "ver": "v1.48",
  "enforce": true
}
```

原厂去掉版本首字符后做数值比较，需要远端值更大、强制标志为真且没有进行中的升级。示例版本属于原厂更新判定字段，不表示镜像内社区固件的版本。升级清单不要混入 `device_id`，否则可能进入激活响应分支。

MD5 必须根据实际提供下载的文件计算；它用于内容校验，不是原厂私钥签名。原厂检查更新走 HTTPS，镜像 URL 的解析路径同时支持 HTTP 和 HTTPS，实际下载兼容性仍需测试。

### 为什么修改 DNS 后未必立即升级

A1 的自动检查涉及激活状态、时间同步和检查时段。已追踪的定时器间隔为一小时，并要求设备时间字符串中的小时为 `18`。这不等于用户本地晚上六点一定立即更新，具体时区和调度还需实测。

长连接另有 OTA 指令路径，但完整会话、分帧和状态交互尚未复现。它目前不能写成向设备发送一个 JSON 就可强制触发的操作。

### 兼容服务上线前需要具备的能力

1. 实现设备需要的激活与升级响应，按目标设备选择适配镜像。
2. 在 HTTPS 443 上兼容原厂旧 TLS 客户端，包括证书算法、密码套件及可能缺少 SNI 的情况。
3. 提供可下载的完整镜像，并记录实际请求、传输和内容校验结果。
4. 由目标原厂设备证明 TLS 握手、更新触发、下载、安装、重启及功能均通过。

静态调用显示检查更新时未启用 CA 证书验证，但这不能代替旧 TLS 兼容测试。目前缺少完成上述验证的公共服务，因此没有可供用户直接照填的 DNS 地址。

## 6. 怎样判断刷机成功

无论走内网还是公网，都需要确认：

1. 设备重启后可按迁移包说明访问，能读到预期的型号与社区版本。
2. Wi-Fi、页面和净化器基本控制正常，原有配置是否保留符合迁移包说明。
3. 再次断电上电后仍能启动、联网及正常使用。

HTTP 成功、文件下载结束或设备断开连接都只是中间结果。公网服务日志应区分“检查到更新”“下载完成”和“设备已运行新固件”，不能合并成一个成功状态。

## 7. 常见问题

| 问题 | 处理 |
| --- | --- |
| `/config-read` 不通 | 先确认设备已联网、IP 正确且双方未被隔离 |
| 修改 DNS 后没有请求 | 检查设备实际使用的 DNS、缓存、激活和时间状态，再判断是否到了检查时机 |
| 已有 `.raw` 或 `.signed` 文件，能否直接上传 | 依据发布方对首次迁移路径的说明确认；后缀不能代替兼容性验证 |
| 设备下载完成但没有正常启动 | 保留服务日志和文件哈希，不把下载成功当作安装成功 |

本文仅完成原机备份的静态分析与操作说明，未连接或刷写设备。
