## 实现约束

- HTTP/MQTT 的 v1 业务共用一个互斥保护的准入预算。堆保留目标 16 KiB；每次业务估算 12 KiB + 请求正文长度的两倍（上限 8192 B）。已有预留和实际空闲量同时考虑，属于保守准入估算，不是分配器硬配额。
- A1/M1 复用描述符 FIFO，当前容量为 2，HTTP TCP 连接上限为 3（一个处理、两个等待），OTA 时收紧为 2，由一个业务线程执行。内存不足时不申请业务正文/JSON，25 ms 检查余量，最多等待 2 秒。等待后恢复则继续同一请求；等待超时或已接受连接的队列满返回固定 HTTP 503 `busy`。等待时间从当前请求被工作线程取出后计算，不是排队总耗时。SDK 连接层超限拒绝仍可能表现为连接失败。
- TC1 复用 SDK 有界连接/串行分发，v1 处理函数在申请正文/JSON 前执行同样的等待。没有增建按请求分配的线程或业务队列。
- MQTT 回包队列固定 4 槽，每槽增加 160 B 预留忙响应；低内存输入不解析业务 JSON、不执行命令，只用有界扫描恢复顶层合法请求编号并排队回 `busy`。不从 MQTT 回调内发布。队列满保留既有连接但丢弃超额命令，不能保证无限负载每条都有忙响应。
- 普通业务正文/JSON 仍在准入成功后动态申请，释放后供后续请求复用。状态 JSON 在发送前释放，只保留文本。MQTT 状态上报序列化内存失败跳过该次上报，真实网络发送错误仍按原流程处理。
- `/api/v1/memory` 保留现有认证，使用栈格式化，不创建业务 JSON；显示空闲/已分配/空闲块数/uptime、预留目标、在途预留、在途数、等待数、拒绝准入尝试数和采样最低空闲。拒绝数包含等待重试，最低值不是分配器连续水位。
- 零新增业务分配不等于协议栈零分配。TCP 收包、SDK HTTP 头处理等仍可能占堆；维持有界连接和队列，不能无限保持 TCP。保护不覆盖第三方/旧协议所有独立分配路径，也不保证系统余量永远不低于 16 KiB。

## 第二版压力边界及修正

A1/M1 `110a79`（TCP 8、等待队列 4）均签名 OTA 成功。A1 的 2、4 HTTP + MQTT 4/秒各 45 秒无重启，请求均正常或 busy；8 HTTP 含 8 KiB 填充时，37.4 秒触发低余量停止线。业务/轻量接口直接采样最低 22808 B，但准入点最低仅 **1320 B**；没有重启，配置/联动/控制状态保留。12 并发未运行。这说明业务 JSON 准入无法约束协议栈收包内存，不能以较高的慢速状态采样掩盖准入点低水位。

第三版 A1/M1 `9bf1ab` 改为 TCP 2、FIFO 1，但真实浏览器启动验证发现能力读取被连接复位丢失，网页验收 FAIL。随后将候选调整为 TCP 3、FIFO 2，容纳网页初始化的三路读取，同时限制滞留正文数量；新候选实机验收进行中。四台联动上限独立于 HTTP 连接数量。该容量收紧会降低并发吞吐，超额连接不保证返回应用层 busy。

TC1 `4de1ad` 的 1、2、4 HTTP + MQTT 1/秒均无重启，但 4 并发有 8 次 HTTP 连接复位。检查发现被拒绝的 POST 存在未读正文立即关闭风险，`332e6b` 增加固定 128 B 栈缓冲、最多 8192 B/100 ms 的清理；不解析或执行被拒绝请求。真实 TCP 主机测试验证完整 busy 和缺失正文的有界退出。实机复测 4 并发仍有 5 次连接复位，故这不是完整根因修复，响应服务质量仍为 PARTIAL；资源/配置健康通过，MQTT 错误计数未增加。
