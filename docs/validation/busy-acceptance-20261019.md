# 受控 busy 与内存/重启压力验收（2026-10-19）

基于 `perf/main-memory-budget-20261019`；实机 A1/M1 `0.9.13-e6cb0e`、TC1 `0.9.13-ada888`。本轮只做只读压力与恢复验证。实现及历史边界见 [内存准入报告](memory-admission-20261019.md)。

结论：三台当前版本均未达到所有请求正常或受控 busy 的标准；有限压力期间未发现重启、未触发 8192 B 停止线。全局零 OOM 缺少分配失败计数，不能判为已经证明。配置/控制最终保持，三台最后在途、预留、等待均为零。

## 验收定义与证据边界

1. 受控响应：HTTP 20 秒 socket 超时范围内返回 200/ok 或 503/busy；MQTT 对唯一 request_id 在 4 秒截止内返回非 retained 的 ok/busy。复位、连接错误、超时及不匹配回包均不能算 busy。HTTP 超时为 socket 操作超时，不能作为整个请求的硬截止；具体阶段和请求时长单独记录。
2. 内存与重启：身份/版本、开机时间、健康、配置及控制状态保持；直接或准入点采样低于 8192 B、重启、看门狗故障或控制状态变化则停止。16 KiB 是准入目标，不是 SDK 全局配额。
3. SDK 没有暴露全局分配失败次数和最大连续空闲块。采样余量正常、无重启只能证明已测场景表现，不能证明全系统从未有分配失败或无限时间不 OOM。主机故障注入用于验证业务拒绝、固定 busy 及清理路径，不能替代物理 SDK 证明。

一个执行器逐台运行，压力只调用 status.get/config.get；后续隔离测试用工作线程零替换一次负载来读取 /api/v1/memory，不额外增加探针连接。HTTP 与 MQTT 均用唯一编号，拒绝 retained 回包。MQTT 每秒最多一批 4 条、批内间隔 50 ms；缺失回包时等待会降低实际发送频率。HTTP 每线程请求间隔 150 ms。大正文为填充至 8192 B 的合法只读 JSON；监控 GET 不填充。HTTP 失败率超过 20% 不再升阶，各阶段移除负载并恢复检查。

## 设备汇总

| 设备 | 所有请求均正常或 busy | 未发现重启 | 配置/控制保持 | HTTP 失败数 | MQTT 4 秒超时数 | MQTT 错误增量 |
| --- | --- | --- | --- | ---: | ---: | ---: |
| A1 | FAIL | PASS | PASS | 194 | 0 | 0 |
| M1 | FAIL | PASS | PASS | 69 | 84 | 4 |
| TC1 | FAIL | PASS | PASS | 6 | 0 | 0 |

A1 隔离普通 2 客户端阶段 199/199 HTTP 正常，MQTT 92 正常、88 busy、0 超时，说明有限负载下准入有效；但 4 客户端和大正文仍有连接失败，不能据此认定全入口受控。A1/M1 配置的 TCP 硬上限为 2、FIFO 为 1；接收队列可回固定 busy，但 SDK 连接层可先行拒绝。A1 4 客户端有 191 次 ConnectionResetError 和 1 次 URLError；M1 4 客户端有 64 次 ConnectionResetError 和 1 次 URLError。不能仅据错误类型将每次失败归因于同一机制。

M1 普通 2 客户端 HTTP 40/40 正常，但 MQTT 10 正常、2 busy、32 次 4 秒超时；4 客户端 MQTT 44/44 超时。移除压力后身份/版本及配置保持且恢复在线，普通两阶段 MQTT 错误累计增加 4。内存采样不能解释全部回包丢失，MQTT 错误也不能单独证明 OOM。无 HTTP 压力的后续诊断 20/20 得到受控回包：18 正常、2 busy，最大延迟 1.047 秒，MQTT 错误增量 0、无重启。这只能说明该时段移除 HTTP 后恢复，不能证明之前失败的根因。

TC1 8 客户端最长 HTTP 为 22.022 秒；2 客户端 248 次 HTTP 与 180 条 MQTT 全部受控，但更高并发及大正文有失败。逐请求延迟与失败类型见 public/latency-and-failures.json。

## 首次失败及人工操作干扰与复测

TC1 首次严格预检在读取 schedules.get 时 RemoteDisconnected，未开始压力；首次记录保留为 FAIL。之后以新证据目录重试，不能以重试通过覆盖首次失败。

初轮 A1 采用额外 HTTP 内存探针：1 客户端 HTTP 121/121 正常、MQTT 92 正常/75 busy/1 超时；2 客户端在约 23.2 秒停止，HTTP 105/10/18，MQTT 44/48/1。停止原因为风扇请求由关变开及联动 max_speed 变化。用户明确确认当时有操作并表示之后保持不动。原结果完整保留为受干扰的独立证据，不与隔离阶段合并、不恢复用户状态；其超时/复位也没有删除。之后以新状态重新捕获基线并运行上表。

未运行 A1/M1 8、12 客户端及 TC1 12 客户端；A1/M1 在 4 客户端 HTTP 失败率超过 20% 后不再升阶。首次 TC1 预检失败后单独重试，未覆盖或删除首次错误。

## 主机与证据

`SANITIZE=1 bash tests/run.sh` 本轮完整通过，包含共享预算、同 FD 等待/超时、固定 busy、JSON 分配/序列化失败及 MQTT 队列满/释放路径。最初误将 C 测试 `test_mqtt_service.c` 当 Python 模块调用，出现 ModuleNotFoundError；该调用错误日志保留，随后完整脚本按正确路径执行通过。
