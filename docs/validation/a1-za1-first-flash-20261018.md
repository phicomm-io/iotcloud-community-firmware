## 代码路径与修复

SDK 的 `mico_system_para_storage.c:MICOReadConfiguration()` 检查 MiCO 参数分区 CRC 和 `micoSystemConfig.magic_number`，不会检查应用自定义的 `A1_CONFIG_MAGIC`。CRC 有效的其他固件参数不会自动触发 `appRestoreDefault_callback()`。

原 `A1/main.c:application_start()` 将应用标识不匹配与社区配置版本不支持合并为同一个错误，直接返回。已核对当前工作区与 `v0.9.10` 标签均有此逻辑。

修复分开处理两种情况：

1. 应用标识不匹配：清空应用存储结构、生成社区默认值，并通过 SDK 保存。记录 `foreign_layout_reset` 后继续启动，需要重新配网。
2. 应用标识属于社区，但版本不支持：继续拒绝启动并保留原配置，避免降级时误清空未来版本数据。

只初始化应用数据，不调用整片擦除或 SDK 系统恢复。保存失败仍停止启动；v1–v6 迁移继续保留现有 Wi-Fi、名称、滤芯和任务数据。

### 状态接口内存分配失败及配网内存优化

用户随后按状态接口检查步骤反馈 `message: Out of memory`。这已提供应用回复构造分配失败的证据，不能再仅以“发送容量模型”解释所有现象。`send_json()` 在上层回复对象为空时返回该提示；该路径下完整状态 JSON 的构造已经失败。尚无该机空闲堆总量、最大连续块或 SDK 网络池数据，不能判断是否属于堆耗尽、碎片或特定池不足，也不能证明之前零正文一定由同一次分配失败引起。

核对 A1 启动代码与构建产物：

- 网页数组在 Flash 的 `.rodata` 中，不是 58,267 字节堆副本，设备也不解压页面。
- 原启动流程即使没有路由器连接，也创建 MQTT 线程并申请 16,384 字节栈；其循环在未联网时只休眠，依然占用这份预留资源。
- 原 6 个业务线程申请栈合计 59,392 字节（58 KiB），不含 watchdog、SDK、自身线程控制块和业务动态分配；这是申请量，不是实机堆统计。
- 初次未保存 SSID 时只启动 SoftAP；提交候选凭据后保留 AP 并连接 STA，取得当前 SSID 的 IP 后才停止非手动请求的 AP。没有证据证明用户首次页面加载失败时已经处于 AP/STA 并行阶段。

本次针对首次配网调整：

1. 将 MQTT 创建移到网络线程，在确认路由器连接与有效 IP 后执行。配网 HTTP 和本地硬件线程先于网络线程申请栈，避免连接较快时 MQTT 抢先创建。
2. 创建成功后不再重复创建；创建失败至少间隔 30 秒后由网络线程重试，未联网、OTA 和待重启期间不创建。已运行的 MQTT 保持其原有断线重连逻辑，不强行删除线程，也不降低运行栈预算。
3. 新增经过现有网页认证的 `GET /api/v1/memory`。用固定 256 字节栈缓冲格式化 SDK 的空闲内存、已分配量、空闲块数与 uptime，不创建 JSON 对象树；可以在完整状态 JSON 构造失败时尝试取样。网络发送仍依赖 SDK，不能承诺任意资源耗尽时都能返回。
